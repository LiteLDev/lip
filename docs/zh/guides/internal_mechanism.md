# 内部机制

本指南说明 lip 的底层工作方式。

## 架构

lip 提供两个主要入口：

1. **CLI（`lip`）**：独立命令行工具，内置包管理逻辑，**不依赖**守护进程。
2. **Daemon（`lipd`）**：独立进程，供外部应用（IDE、GUI、脚本）以编程方式调用 lip。

CLI 与 Daemon 共享同一套核心逻辑，保证无论通过哪种接口，行为都一致。

Daemon（`lipd`）通过 **stdio 上的 JSON-RPC** 通信，使工具无需为每个命令反复拉起进程，也无需解析文本输出。

## 包解析

lip 不使用中心化的包注册表或模块代理。像 `github.com/user/repo` 这样的包路径直接对应 git 仓库 `https://github.com/user/repo.git`，lip 通过内置的 git smart-HTTP 协议（第 2 版）客户端与其通信。**无需安装 `git` 命令行工具**，lip 也从不调用它。

- **版本**：lip 通过 `ls-refs` 列出仓库标签（只请求 `refs/tags/v*`）。可用版本即形如 `v<semver>`（例如 `v1.2.3`）的标签；不是合法语义化版本的标签会被忽略。附注标签会被解析到其指向的提交。
- **清单**：读取某个版本的 `tooth.json` 时，lip 只获取该标签提交的树对象（使用 `filter blob:none` 的浅层部分获取，不传输任何文件内容），然后只下载 `tooth.json` 这一个 blob。因此无论仓库多大，解析依赖时每个版本只需几 KB 流量。
- **安装**：包版本的文件列表同样来自这棵树。lip 用所选变体的 `self` 资源放置规则匹配该列表，然后在一次批量请求中只下载匹配到的文件。未被任何放置规则匹配的文件不会被下载。
- **完整性**：每个下载的对象都会按其 git 对象 ID（SHA-1）校验。
- **缓存**：下载的文件按对象 ID（`git-blob:<id>`）存入全局缓存，相同的文件只下载一次，可在不同版本和不同包之间复用。标签列表和树对象仅在单次命令执行期间缓存在内存中；每次运行都会重新查询标签，因此被移动的标签会立即生效。
- **重定向**：已重命名或转移的 GitHub 仓库会通过 GitHub 的 HTTP 重定向自动跟随。包仍使用请求时的路径，`github.com` 的所有者和仓库名不区分大小写。
- **代理**：若配置了 `github_proxy`，对 `github.com` 仓库的请求会先经由该代理发送；若代理请求失败，lip 会直接向 `github.com` 重试。从 `github.com` URL 下载发布资源时遵循同样的规则。

只有当某个版本的标签仍存在于仓库中时，该版本才能被安装。目前只支持可通过 HTTPS 访问的公开仓库。

标签处的清单决定包的内容，但不决定包的身份：若其 `tooth` 路径或 `version` 与请求的包路径或标签不同（例如仓库被重命名后），lip 会给出警告，并以请求的路径和版本记录该包。

## 清单校验

`tooth.json` 的格式由仓库 `schemas/` 目录中的 JSON Schema 描述：当前格式（版本 3）为 `manifest.schema.json`，旧格式为 `manifest.v1.schema.json` 和 `manifest.v2.schema.json`。这些 schema 供编辑器和其他工具使用，lip 本身不执行 JSON Schema 校验。

- **校验**：加载清单时，lip 会将其解析为类型化模型，并拒绝无效值，例如不是合法 Go module path 的 `tooth`、无效的 `version`、标签或变体标签，以及错误的 `format_uuid`。
- **版本**：lip 通过 `format_version` 字段判断如何解释文件。格式版本为 1 或 2 的清单会在读取时于内存中转换为版本 3；如需将文件改写为当前格式，请运行 `lip migrate`。

## 工作区状态

lip 在工作区根目录的锁文件 `tooth_lock.json` 中维护已安装包状态（参见[锁文件](../concepts/lockfiles.md)），记录：
- 用户显式请求的包与隐式依赖；
- 精确安装版本；
- 文件放置位置与方式等元数据。
